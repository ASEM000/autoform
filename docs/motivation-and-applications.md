# Motivation and Applications

A program often needs to do more than produce an output once. The same computation may need to run across examples, expose an intermediate result for inspection, or propagate feedback from its output to its inputs. Implementing each behavior separately repeats knowledge of the program structure. A change to the original computation can then require changes to several implementations.

A similar problem arises when writing the forward and backward passes of a neural network by hand. Changing the network can require changes to both passes. Automatic differentiation frameworks avoid this repetition by composing backward rules for individual operations.

`autoform` applies this principle to programs over text, numbers, and user-defined types. Extensions specify spaces for values and feedback and rules for operations on those values. The rules compose into whole-program transformations. Separate execution interfaces allow the same program to be inspected or run under different policies. These are building blocks for higher-level methods; the application still supplies its objectives and decisions.

A grading program illustrates how these pieces fit together. A language model uses a text rubric to produce a grade, and an arithmetic operation adjusts the score. The program's {py:func}`pullback <autoform.pullback>` returns text feedback for the rubric and a numerical gradient for the points adjustment. The following applications use the same principle of deriving additional behavior from a shared program.

| Application | Use |
| --- | --- |
| Optimization | An optimization method uses these building blocks in a feedback loop. It supplies an objective, evaluation data, and an update rule. A transformed program evaluates the objective and computes feedback; the update rule uses that feedback to revise the parameters for the next evaluation. Different optimization methods can reuse the same program and transformation rules with different update policies. <a href="concepts/transforms.html?transform=pullback#updating-inputs">Updating Inputs</a> shows a simple update loop. |
| Sensitivity Analysis | {py:func}`pushforward <autoform.pushforward>` and {py:func}`pullback <autoform.pullback>` propagate changes or feedback even when no input is being optimized. The registered spaces and rules determine the meaning of each signal. An extension could use a structured critique for a custom text value rather than a numerical gradient. |
| Evaluation and Debugging | {py:func}`batch <autoform.batch>` evaluates a program across examples. Execution contexts can capture checkpointed results or substitute controlled values to investigate a failure and test what happens downstream. [Capture and Replacement](concepts/execution.md#capture-and-replacement) shows this workflow. |
| Ranking | {py:func}`weight <autoform.weight>` scores an execution, and {py:func}`batch <autoform.batch>` applies the scoring program to several candidates. The caller supplies the candidates and decides how to compare the scores. [Tool Ranking](recipes/llm/tool-ranking.md) applies this pattern to tool selection. |
| Execution Policies | A custom interpreter can record operation results and tags. A runner can pause at a marked result for human review. A configured model client can manage routing and retries. The application supplies the checks and responses needed for a reliability workflow. [Human Review](recipes/execution/human-review.md) shows one such runner. |
| Adaptive Workflows | Structured state, branches, and bounded loops support programs that choose tools and revise results. [Tool-Use Agent](recipes/llm/tool-use-agent.md) traces such a program, then applies {py:func}`batch <autoform.batch>` and {py:func}`pullback <autoform.pullback>` to it. |
| Efficient Execution | {py:func}`sched <autoform.sched>` groups independent calls for concurrent asynchronous execution. {py:func}`dce <autoform.dce>` removes unused computation, and {py:func}`memoize <autoform.memoize>` reuses matching results. Fixed context can also be computed during tracing while task inputs remain dynamic. [Concurrent Execution](concepts/execution.md#concurrent-execution) and [Static Context](concepts/tracing.md#static-context) show these cases. |

New domains can extend these applications by registering types, spaces, operations, and the rules needed by each transform. [Array Extension](recipes/extending/array-extension.md) demonstrates this pattern for NumPy arrays. Transformation order and the available rules determine which combinations a program supports.
